01Purchase intent

Case study 01 / Transactional state & remote effects

Repeated checkout.
Controlled access.

Checkout attempts and callback retries can repeat downstream access work. A purchase intent groups matching owner-and-plan attempts under one active lifecycle.

  • Rust
  • Transactional claim
  • Callback processing
  • State modelling

Guarantee boundary

The claim controls repeated access processing. It does not prevent the provider charging twice or establish distributed exactly-once behavior. The database commit and remote access RPC do not share a transaction.

The mechanism

Find the matching unused owner-and-plan intent, or create one. Each checkout offer retains a snapshot of its token; matching attempts share the active token.

An eligible callback atomically consumes the intent, records the payment reference, and rotates the token before the remote access RPC. A duplicate claim skips repeated access and requests a best-effort support ticket.

The design choice

The intent represents a purchase lifecycle; the offer represents an individual attempt. The offer's token snapshot remains useful after the current intent token changes.

This is temporal correlation, rather than a stable foreign key. A later purchase creates a new active row; a consumed row remains consumed.

What the evidence supports

A reviewed feature snapshot and historical local verification support matching registered-buyer token reuse. The models describe the claim and dispatch contracts.

Production rollout, fresh concurrent runtime verification, and business-impact measurements are not asserted.

Compatibility paths and unresolved recovery

Fail-open paths: a missing legacy token or a claim-store error continues through compatibility handling. Checkout creation errors propagate. Strict suppression is therefore reduced when the claim cannot be established.

Ownership validation: anonymous visitor and checkout-session precedence differ in the reviewed creation and lookup paths. Anonymous reuse remains a known validation gap.

After consumption: a failed access RPC needs recovery or reconciliation. Recurring subscription events retain their existing processing path. Useful measurements include suppressed dispatches, claim errors, ticket-delivery failures, and downstream failures after consumption.

Known limit: legacy tokens and claim-store errors fail open; anonymous reuse is not verified. Review this mechanism as a feature snapshot.

02Distributed telemetry

Case study 02 / Durability, lineage & coverage

Collect observations.
Preserve the evidence.

Two node agents push bounded telemetry to a collector. A workstation fetches retained records, archives the raw evidence, and projects typed rows into a local SQL store.

  • Rust
  • mTLS gRPC
  • redb
  • zstd
  • GreptimeDB
  • PostgreSQL wire

Coverage boundary

The collector retains records for 36 hours, regardless of workstation acknowledgement or availability. A cursor behind that history yields an explicit gap. Missing observations remain unknown; they are not zero.

The mechanism

Agents initiate outbound mTLS gRPC publishing. The collector commits to durable redb storage before acknowledging a batch. The workstation initiates authenticated cursor-based fetches.

Compressed raw parts, checksums, and a durable manifest precede durable fetch-checkpoint advancement. Typed SQL projection uses GreptimeDB through the PostgreSQL wire protocol, with a local-only listener.

The design choice

Structural identity includes host, stream, process run, source generation, and sequence. Identical bytes replay safely; changed bytes under the same identity are a conflict.

A raw archive plus SQL projection keeps evidence replayable and questions convenient. The cost is two representations, explicit checkpoints, and projection-retry work.

What the evidence supports

Source contracts and existing test coverage describe replay, conflicts, restart continuity, backpressure, and retention gaps.

The portfolio does not claim a new production failover experiment, fixed query latency, or uptime. Observation age, delivery lag, and gaps qualify every finding.

What happens when the pipeline falls behind?

Within retained history, the workstation resumes from its durable cursor. Beyond the 36-hour horizon, the pipeline records a gap and marks coverage incomplete. Workstation acknowledgements do not extend retention.

Projection failures leave archived evidence available for retry or replay. Collector storage pressure produces visible publishing backpressure. Monitor observation age, retry rate, archive integrity, projection lag, explicit gaps, and collector disk headroom.

Known limit: bounded hub storage trades an unlimited offline window for explicit coverage gaps. Collection cadence and archive finalization determine time to query.

03Mobile operations

Case study 03 / Access topology & agent workflow

A mobile terminal.
The existing workspace.

A phone reaches the workstation through a dedicated relay. The terminal provides access to OpenCode, scoped agent tasks, and the local telemetry store already on the workstation.

  • Termux
  • WireGuard
  • SSH
  • OpenCode
  • Local SQL

Evidence boundary

The integrated OpenCode journey models operator-stated practice. It is not a newly measured mobile experiment. A reachable workstation can hold stale telemetry; access success and evidence freshness require separate checks.

The access path

Phone and Termux reach workstation SSH through a WireGuard relay. The SSH session terminates on the workstation, where OpenCode assigns a scoped agent to query local SQL.

The agent returns findings with freshness, lag, and gap evidence. The operator reviews the interpretation and decides the next action.

The topology choice

The relay and telemetry collector are separate servers. Six infrastructure endpoints participate: two producers, collector, relay, workstation, and phone.

“Triangulation” names the phone–relay–workstation access topology. It does not mean statistical corroboration. Software roles inside an endpoint do not add servers.

What the evidence supports

Operational documentation records an end-to-end WireGuard mesh and key-based Termux SSH connection.

That supports the access path. The integrated agent journey remains a model of stated practice; no uptime or productivity gain is claimed.

Known limit: relay and workstation availability determine access. A tunnel handshake alone does not prove SSH reachability; local-data age determines how current an answer can be.
